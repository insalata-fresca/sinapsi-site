A case study in platform engineering for AI agents

Run AI agents like a platform, not like a chat.

Sinapsi is how I manage AI agents the way an organisation manages infrastructure: one door, one source of truth, and rules that say honestly how they are enforced. I built it, and I run it, on my own servers. This page explains why the same shape can work in an enterprise.

By Stefano Ursino · personal research, no employer or client material

The manifest

Six commitments the platform is built on

  • A bounded door, never raw access.An agent gets a small, audited surface to a system, not its credentials.
  • One source, two consumers.People and agents read the same service, and a check proves they get the same answer.
  • Control from reversibility, review and scope.Gating every command does not scale. Making work easy to undo, reviewed and narrow does.
  • Say how each rule is enforced.A rule labelled as enforced when it is not does more harm than no rule.
  • Authority is earned.Autonomy is granted per class of change, decays if unproven and can be revoked in one move.
  • Work is a mission, not a chat.Bounded scope, an owner, a full context bundle and an independent check on the way back.

What this does not show

  • It is one operator on a home-scale lab across two sites. There is no multi-tenant load, no cost model and no organisational change to manage.
  • Some authorization layers still run in shadow mode on purpose. I observe before I enforce.
  • The claim is the shape of the platform and the discipline around it. It is not a claim of enterprise readiness.
Field notes

What running it taught me

Measure the default

A fleet default can be set upstream

Running Claude Code across many hosts, I found that the starting permission mode of sessions started from the app was assigned by the service, not by host configuration. I tried the launch flag, user settings and the managed settings tier. None changed it, and public bug reports described the same behaviour. I kept the control in the gateway and the always-on hooks, where I own it. It later changed upstream with no change on my side.

Delete with evidence

Rarely used is not dead

An audit of my own repository refuted about two thirds of the "this is dead" claims. A yearly certificate rotation and a recovery path are both rare and both load-bearing. Deletion now needs positive evidence, and disabling comes first.

Prove the claim

A green pipeline proves a job exited zero

Success is verified on the host or on the event bus. A same-answer check does this for the control room, and the decision trail does it for every authorization.

Register what runs

A register proves shape, not completeness

A census of the fleet found third-party software that nobody was updating. A check can show that the register is well formed. It cannot show that it is complete, so the platform reports the gap the morning after.

Case study

The control room

The human face of the platform: one cockpit for the person, one door for the agents, and one source of truth behind both.

The problem

A fleet of agents is only useful if I can see what it is doing and answer yes or no from wherever I am. Chat threads do not give me that. Decisions get lost, and each tool describes the lab a little differently.

What I built

  • A decision inbox called Now. Anything an agent cannot decide alone lands as a card with the evidence and two buttons. The answer is recorded once and applied once.
  • A mission ledger. Work is split into bounded missions, each with an owner, a status and a link to the change that did it. I approve goals. An orchestrator session starts the work and checks what comes back.
  • A relationship map. One read-only service knows how the parts of the platform connect. The cockpit and the agents read it through the same door.

How it was built

  • Journey first. I modelled who uses it and which decision they face before drawing any screen.
  • Phone first. A screen counts as done only after I have looked at a real rendering on a phone.
  • Separation of duties. The session that builds a change does not merge it.
  • Proof over claims. A same-answer check compares what the cockpit shows with what an agent receives and reports whether they match.
  • Always current. The map follows a merge by itself, in under a minute and without a restart.
Essays

The thinking behind it

Fourteen first-person essays on building and operating software with AI agents. They hold the reasoning, not the tooling. Every example is invented and no real system details appear. A fifteenth, on honest enforcement labels, is in draft.

  1. The manifesto

    Control comes from reversibility, review and scope, not from gating every command.

  2. Documentation That Cannot Lie

    Make the running system the source of truth and flag any claim that no evidence backs.

  3. Grounding the Agent

    Memory inside a session is a cache with no invalidation. Ground every session in a live source.

  4. The Trust Plane

    Never hand an agent raw credentials. Route every action through a policy-enforcing, audited plane.

  5. Proving You Didn't Break It

    For migrations, run old and new side by side on real input and diff the behaviour.

  6. Journey-First Design

    Model the user, the job and the decision points before any pixel.

  7. Deterministic UI

    Every surface traces to an authored spec and a shared design canon.

  8. The Council

    One model is a single point of failure for judgement. Consult several and weigh, do not vote.

  9. One Stack, Reproduced

    One canonical stack, with conventions shared as versioned packages.

  10. Missions, Not Chats

    Structure work as governed missions with a complete context bundle.

  11. The Tool Plane

    An agent is only as safe as its tools, so treat the tool surface as infrastructure.

  12. Identity and Secrets Without a Human in the Loop

    Scoped identity per actor and secrets delivered at runtime, never pasted.

  13. The Decision Trail

    Emit every decision as a typed, correlated event so "why was this allowed?" is one query.

  14. Continuous Trust

    Authority to proceed alone is earned, decays if unproven and can be revoked in one move.
