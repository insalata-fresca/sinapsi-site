A case study in platform engineering for AI agents

Run AI agents like a platform, not like a chat.

Sinapsi is a development factory of AI agents, the platform of services it runs on, and the rules and knowledge that guide both. It runs on my own servers. My hypothesis is that the same responsibilities recur in an enterprise.

By Stefano Ursino · personal research and architecture studies

One failure, start to finish

A green deploy, and the service was down

  1. SymptomA deploy finished green. The service it had just reconfigured was not answering.
  2. What I sawThe restart had returned quietly. The daemon aborted on a bad line a moment later, and nothing reported it.
  3. What I changedFor anything that can refuse to start: validate with its own test mode, restart, then assert it is alive with one real probe.
  4. Covered nowOne route, for one kind of change, runs that sequence in code.
  5. Still openEverywhere else it is a habit. A partial recovery still looks healthy if I check a neighbour.

The manifest

Eight commitments

  • A bounded door, never raw access
  • One source, two consumers
  • Control from reversibility, review and scope
  • Say how each rule is enforced
  • Authority is earned
  • Work is a mission, not a chat
  • Publish once, keep it current, serve it
  • Thin applications on shared state
From a home server to an enterprise

A transfer hypothesis

What I expect to recur in a larger organisation. I have one operator, no tenant isolation and no cost model, so read it with the limits below.

In my labIn an enterprise
One gateway for every agent call→Central policy enforcement point
Cockpit and agents read one service→One catalog for people and agents
Rules as records, enforcement stated→Control library with real status
Green, yellow, red by blast radius→Risk-tiered approval for agent actions
The builder never merges→Change management for agent work
One knowledge service, many domains→Knowledge base with access per identity
Event bus today, Streamhouse as a design→Shared current state
Two sites and a repair path→Multi-region and break-glass

What this does not show

  • One operator, home scale, two sites. No multi-tenant load and no cost model.
  • The evidence page holds one mission record without cost, a six-run injection pilot and two hook fixture sets. There is no baseline comparison and no test of the gateway itself.
  • Some authorization layers run in shadow mode on purpose.
  • The data platform is a design study, not built here.
  • The claim is the shape and the discipline, not enterprise readiness.
Field notes

What running it taught me

A fleet default can be set upstream

I measured three host settings before finding that the service assigned the mode. The control stays where I own it.

Rarely used is not dead

An audit of my own repository refuted about two thirds of the "this is dead" claims.

A green pipeline proves a job exited zero

Success is checked on the host or on the event bus.

A register proves shape, not completeness

A census found software that nobody was updating.
